# GIFTED — Политика публикации Alpha
Вступает в силу после независимой проверки и включения PR #33 в main. Product Owner 24.11.2026 утвердил отказ от обязательного GitHub approval второго аккаунта и сообщил об изменении настройки. Это не отменяет независимую инспекцию.
- Все изменения через PR; прямой push в main и обход защиты запрещены. Обязательные alpha-regression и разрешение обсуждений сохраняются.
- Claude Code — Builder, не выполняет merge и не одобряет свою работу. ChatGPT Architect ведёт очередь; независимый Inspector (отдельный процесс, не автор реализации) проверяет фактический diff, требования, тесты и точный HEAD SHA.
- Inspector фиксирует в PR вердикт APPROVE / CHANGES REQUESTED / INSUFFICIENT EVIDENCE, SHA, доказательства, ограничения и findings. Это запись инспекции, не GitHub approval. Новый HEAD требует повторной проверки.
- L0: ограниченные исправления документации, тестов, опечаток и проверенной мелкой косметики; Architect может разрешить публикацию после всех проверок. L1: игровой код, интерфейс, PWA, архитектура — явное разрешение Product Owner на публикацию. L2: правила, баланс, экономика, платежи — отдельное продуктовое решение до реализации и разрешение на публикацию. Защищённая инфраструктура и документы полномочий требуют отдельного разрешения владельца.
- Merge выполняет Architect или Product Owner только после независимого APPROVE на текущий SHA, зелёных обязательных проверок, отсутствия существенных нерешённых замечаний и конфликтов, соответствующего разрешения и соблюдения защиты GitHub. При отсутствии доказательств — BLOCKED. Никакого автоматического merge или активации событий.
- Независимая инспекция теперь процессуальная, не технически обязательная проверка GitHub. Не выдавать комментарий за формальное approval. При серьёзной регрессии остановить публикации и подготовить revert PR.
- PR #32 и прежние предложения автоматического approval не активируются; не сливать их в прежнем виде. Перед денежными наградами пересмотреть модель безопасности.

## Дополнительные обязательные ограничения
- Inspector не изменяет проверяемый PR и не выполняет его merge. Каждое замечание содержит важность (BLOCKER/MAJOR/MINOR), файл, доказательство и предлагаемое исправление.
- PR-workflow используют только права чтения репозитория и не получают секреты; запрещён запуск недоверенного PR-кода с привилегиями. Новая обязательная проверка вводится только после подтверждённого успешного запуска на main.
- CSS относится к L0 только при локальной косметической правке без изменения поведения, навигации, компоновки, доступности, safe-area или PWA, с подтверждённым визуальным результатом. Иначе L1 или выше по фактическому риску; при сомнении L1.

## Порядок независимой инспекции (Fail Fast)
Утверждено Product Owner 25.11.2026 (Issue #49). Порядок ускоряет возврат найденных дефектов и не ослабляет обязательный CI, критерии приёмки, независимость инспекции, защиту GitHub и полномочия.
1. Inspector фиксирует точный HEAD SHA, на котором проводится проверка, и указывает его в каждой записи инспекции.
2. Сначала выполняются дешёвые этапы:
   - анализ фактического diff, scope и архитектуры;
   - быстрые функциональные, регрессионные и мутационные проверки.
3. Если BLOCKER или MAJOR воспроизведён, Inspector сразу записывает в PR вердикт CHANGES REQUESTED. Запись содержит:
   - SHA;
   - доказательства воспроизведения;
   - findings в обычном формате: важность, файл, доказательство, предлагаемое исправление.

   Ресурсоёмкие проверки (полные турниры, длительные измерения) после этого прекращаются. Каждая невыполненная или прерванная проверка отмечается в записи как NOT RUN или «прервано» с причиной. PR возвращается Builder.
4. Полные турниры и длительные измерения запускаются только тогда, когда на этом HEAD нет блокирующих замечаний. Для длительных турниров обязателен checkpoint, если инструмент его поддерживает.
5. Каждый новый HEAD требует повторной независимой инспекции. Результаты прежнего HEAD не переносятся на новый как доказательство.
6. APPROVE записывается только после всех применимых обязательных и утверждённых проверок на этом HEAD. Проверка NOT RUN или прерванная проверка не считается пройденной. Если такая проверка нужна для приёмки, вердикт — CHANGES REQUESTED или INSUFFICIENT EVIDENCE.
7. Обязательный CI (`alpha-regression`) не останавливается и не пропускается ради экономии ресурсов.
8. Изменение документов полномочий проходит независимую проверку и требует отдельного разрешения Product Owner на публикацию. Builder не выполняет merge.

## Передача управления Architect (Handoff Protocol)
Утверждено Product Owner 26.11.2026 (Issue #54). Game Design (GD) отвечает за продуктовый дизайн: утверждённые Product Owner решения записывает в GitHub Issue со статусом DESIGN APPROVED. Этот статус не означает READY и не разрешает реализацию или публикацию. Architect определяет очередь, зависимости, технические критерии приёмки, риск и перевод в READY. GD не изменяет игровой код или полномочия в обход действующего протокола. Builders Guild (BG) — название роли основного исполнителя, которую выполняет Claude Code.

После каждого действия по разработке BG, Inspector и GD завершают пользовательское сообщение-отчёт отдельным копируемым блоком кода с одной строкой без пояснений внутри:
- BG: `BG <номер PR> done` (например, `BG 47 done`);
- Inspector: `Inspector <номер PR> done` (например, `Inspector 47 done`);
- GD: `GD <номер Issue> done` (например, `GD 53 done`).

Правило действует и для промежуточных результатов, CHANGES REQUESTED, INSUFFICIENT EVIDENCE, BLOCKED и неуспешных действий. Если PR ещё не создан, BG/Inspector используют `BG issue <номер Issue> done` / `Inspector issue <номер Issue> done`. Если номера ещё нет, используют `BG done`, `Inspector done` или `GD done`, указав причину в отчёте. При нескольких задачах — отдельный блок на каждую. Обычное обсуждение без действия по разработке не требует команды.

До передачи управления фактический результат и доказательства записываются в соответствующий Issue/PR в GitHub. Если запись невозможна, роль явно сообщает об этом и не выдаёт результат за сохранённый. Product Owner передаёт Architect только короткую команду; полные отчёты копировать не требуется, кроме отсутствующего в GitHub существенного контекста. Architect самостоятельно читает актуальные записи GitHub, проверяет статус, точный HEAD, применимые проверки, разрешения и определяет следующий шаг. `done` — сигнал передачи статуса, а не успех, READY, APPROVE, разрешение на merge или подтверждение публикации. Все действующие требования к независимости, Fail Fast, CI, защите GitHub и полномочиям сохраняются.
